## 覆盖的回归

- 家庭与房间筛选、搜索、在线筛选、收藏保存、无结果状态。
- 电源开关、滑块键盘操作、枚举类型与动作二次确认。
- 离线设备在界面和 Rust 命令层都禁用控制；属性写入、设备动作和音箱指令均在读取规格或发送网络请求之前拒绝已知离线设备。3 项 barrier 回归曾复现原生校验缺失，加入共享控制校验后全部通过。真实命令拒绝时不显示成功，不改为“已关闭”。
- 当前属性读取失败时不根据缓存猜测电源目标值。
- 场景取消不执行；确认才执行，并只记录本次会话真实发起的操作。
- 音箱目标选择、静默参数、文字指令二次确认。
- 深色主题、手动刷新、隐藏无规格设备及设置跨刷新保存。
- 桌面未登录时不展示演示家庭、不自动请求登录二维码；演示必须主动进入。
- 桌面演示操作绝不调用真实写入/场景命令；浏览器不能冒充扫码登录成功。
- 关闭扫码窗口会取消注册的待登录 ticket。
- Rust 使用 RFC 6229 的 RC4-drop1024 向量、Unicode 往返、参数签名顺序、属性范围/步长/枚举/只读校验及 Windows DPAPI 往返测试。
- Rust 的异步 barrier 回归：A 账号命令在规格等待期间切换至 B 账号，不得改用 B 的凭据发送请求。
- Rust 的二维码请求代次回归：较早开始但较晚完成的请求，不得取消或替换较新的二维码。

## 本机 Windows 链接问题

本机标准资源转换曾失败：`CVTRES CVT1103`、`LNK1123`。定位到自动生成的 `resource.lib` 文件开头是 **`E-SafeNet ... LOCK`**，而非 Windows 资源文件格式。这表明生成文件受到本机透明加密策略影响，并非图标格式损坏或 Rust 类型错误。

排查中使用相同资源描述，通过标准 Windows SDK 生成 `.res` 并转换为 COFF `.obj` 成功，帮助确认资源内容本身有效。没有解密受保护文件、停用安全软件、修改系统加密规则、修改第三方编译依赖或加入绕过脚本。

本项目保留正常的官方 Tauri 构建流程。若标准链接仍被本机策略阻断，需由设备管理员检查编译工具与资源中间文件的授权规则，或在符合组织安全策略的标准 Windows 构建环境运行提供的 CI。**在解决前不能宣称本机已产出可运行 exe 或安装包。** 最终标准构建复验仍在同一资源链接步骤失败。管理员诊断摘要和恢复后的执行清单见 [Windows 构建交接](BUILD_HANDOFF.md)。

## 开发服务问题及修复

- 首次全工作区扫描会包含不相关的工具链/构建文件，导致开发页加载超时。Tailwind 显式只扫描 `src/`，Vite 依赖入口显式设为主 HTML。
- Windows Vite watcher 曾扫描 Rust 原子编辑的临时文件，遇到 `EBUSY`。现在排除了原生源码/target、本地工具、参考仓库、原有无关目录和临时目录。
- 修复后 HTML 响应实测约 3 ms、主模块约 42 ms、样式约 55 ms；13 项交互回归再次通过约 12 秒。这只是当时本地热加载测量，不是普适性能保证。
- Node 将 `process.env` 展开为普通对象后，Windows 的 `Path`/`PATH` 不再等价。启动辅助脚本已统一键名并保留 Node、npm、Rust 的路径，并加入 4 项回归。
